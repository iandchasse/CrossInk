# Silkscreen port of CrossInk

This branch (`silkscreen`) ports [CrossInk](https://github.com/uxjulia/CrossInk) to **Silkscreen**, an open-hardware ESP32-S3 e-paper reader board:

- ESP32-S3-WROOM-1-N16R8;
- a 4.26" 800x480 panel, SSD1677 or the custom UC8279D;
- an FT6336U touch tail alongside eight ADC-ladder keys, with power on IO18;
- 4-bit SDMMC, a DS3231MZ RTC and a TPS923610 front light.

The hardware is described in `de-link_pcb/docs/HARDWARE.md` ([iandchasse/silkscreen-pcb](https://github.com/iandchasse/silkscreen-pcb)).

**A second panel.** `silkscreen-368` is the same board with the Xteink X3's 3.68" 792x528 panel in place of the 4.26" one, and no touch tail ([The 3.68" variant](#the-368-variant)). This page is about the 4.26" board unless a line says otherwise.

**The reference port.** The finished, reviewed port of CrossPoint Reader is `silkscreen-firmware/crosspoint-reader`, branch `silkscreen`. This port carries the same board support into CrossInk, adapted to CrossInk's own code.

**The docs here:**

- [REQUIREMENTS.md](REQUIREMENTS.md): the firmware-facing hardware facts. A verbatim copy from CrossPoint.
- [MODULARITY.md](MODULARITY.md): how the firmware tells the board's variants apart. A verbatim copy from CrossPoint.
- [POWER.md](POWER.md): the sleep budget, the pin states and every battery-drain rule, with the CrossInk file and function that implement it.
- [TEST-SUITE.md](TEST-SUITE.md): a pointer to CrossPoint's hardware test firmware, which CrossInk uses for bring-up.
- [BATTERY-LOG.md](BATTERY-LOG.md): the battery sleep/wake log (the `silkscreen-batlog` build): a pointer to CrossPoint's manual, and what differs on CrossInk.

## Architecture: Silkscreen is data

CrossInk follows freeink-sdk's rule that feature code never keys off a device name. The SDK side is CrossPoint's, shared unchanged: `FREEINK_DEVICE_SILKSCREEN`, `Board::Silkscreen` and the `SILKSCREEN` profile live only in `BoardConfig.h`, and every Silkscreen need is a defaulted profile field or a `FREEINK_CAP_*` mechanism (CrossPoint's PORTING.md, "Architecture", and [MODULARITY.md](MODULARITY.md#how-it-maps-onto-freeink-sdk)). On the app side:

- **Profile data gates the behaviour.** A Silkscreen rule tests a field only `SILKSCREEN` sets, through `BoardConfig::powerPolicy()`, `BoardConfig::hasChargeStatusLadder()`, `hasAdcLadders()`, `TouchConfig::buttonsAlongsideTouch` or `FrontlightConfig`. Otherwise it compiles under a capability flag only Silkscreen sets: `FREEINK_CAP_POWER_POLICY`, `FREEINK_CAP_FRONTLIGHT_PROBE` or `FREEINK_CAP_DISPLAY_PROBE_POLICY`. On every other board the fields are zero, and the flags are off. The `HalGPIO` touch sleep calls compile on every touch build (`FREEINK_CAP_TOUCH`), but only the Silkscreen sleep path calls them.
- **The device macro only registers the build.** `FREEINK_DEVICE_SILKSCREEN` appears only where CrossInk itself registers a device: `platformio.ini`, `src/network/FirmwareBoardTag.cpp` and `src/platform/UsbSerialJtagHandoff.cpp`. `scripts/git_branch.py` knows the two env names. `include/AppCapabilities.h` needed no change: `CROSSINK_APP_CAP_TOUCH=1` and `CROSSINK_APP_CAP_USB_DRIVE=1` match the SDK's `FREEINK_CAP_TOUCH` and `FREEINK_CAP_USB_MSC`.
- **HAL, not SDK.** App code calls `lib/hal`, as AGENTS.md asks, so main.cpp makes no new SDK calls. The HAL gained these wrappers:
  - `HalPowerManager`: `takeReleaseWake()`, `abnormalResetLimitReached()`, `batteryEmptyAtBoot()`, the awake clocks and limits, `radioStartBlockedByBattery()`, `firmwareUpdateBlockedByBattery()`, `noChargeableCell()` and `chargeState()` (the charge-status ladder's decoded state, for USB Drive's cable-pull exit);
  - `HalGPIO`: `begin(deferTouch)`, `startTouch()`, the touch sleep calls, `checkPowerButtonIdle()`, `idleDelay()` and `hasFrontButtons()`;
  - `HalDisplay`: `sleepWithoutDriver()` and `logController()`;
  - `HalClock`: `needsResync()`;
  - `HalFrontlight`: the probe settle and notices.
- **The simulator.** Its HAL is the external `uxjulia/crossink-simulator` library, which this repo cannot stub. Every new HAL call from `src/` is therefore under `#ifndef SIMULATOR` or behind an `include/` or `src/` shim that returns the old answer in the simulator:
  - `include/CrossInkHalFrontlight.h`;
  - `include/DeviceCapabilities.h` `deviceHasFrontButtons()`, `boardHasFrontButtons()` and `boardKeepsKeysBesideTouch()`;
  - `src/network/RadioIdle.h`;
  - `BaseTheme::showsNoBattery()`.
- **Cross-board changes.** Three kinds reach every board:
  - What the shared SDK brings: keyboard layouts and edge keys, glyph-centred header text, atomic settings writes, and SdFat write-back before sleep and USB Drive. Each has a "Silkscreen:" CHANGELOG line.
  - `ButtonNavigator` (`src/util/ButtonNavigator.{h,cpp}`, `8d0408f7`), not gated: a one-key braced list such as `{Button::Left}` used to bind to `std::array<Button, 2>` as `{Left, Back}`, so a Back press also fired the Left handler. Every list method gained a `std::initializer_list` overload and a one-key list is now one key, on every board. Home's cover grid, the folder picker, clipping selection, the interval picker, the on-screen keyboard and the reader menu's sliders no longer react to Back. It has its own CHANGELOG line (the one that starts "A screen that listens to a single key").
  - Size, mostly runtime-gated code and English strings. Against S2, on this host's proxy core and including the three later SDK moves, flash changed by (at the port review):
    - x4-pro: -5.3 KB (GCC now inlines the settings catalog differently there);
    - x4-classic: +3.3 KB;
    - the C3 proxy: +3.5 KB;
    - the Sticky proxy: +3.2 KB.

    RAM grew by 24-40 B. `getSettingsList()` is sensitive to this: a second `std::remove_if` over the catalog once made GCC outline `getBaseSettingsList()`'s lambda as well as inline it (+8 KB on every touch build), so a new condition goes into an existing erase.

  Apart from these three, behaviour on other boards is unchanged. `HalPowerManager::startDeepSleep()` on x4-pro and x4-classic was checked instruction-identical across the S4 change.

## Defaults chosen

The user's decisions for this port:

- **Touch and keys from the start.** `CROSSINK_APP_CAP_TOUCH=1`. CrossInk already lets keys and touch coexist (a key press reveals the selection cursor), but treated "touch" as "no front keys" at some sites. Only those front-key gates now ask `hasFrontButtons()` (`!hasTouch() || TouchConfig::buttonsAlongsideTouch`) through `include/DeviceCapabilities.h`:
  - the theme hint bands (Base, Lyra, RoundedRaff, Minimal, Dashboard) and `UITheme::getMetrics()`'s hint-band height;
  - the Library, Controls, Reader and TTF option layouts;
  - clip selection;
  - the keyboard's bottom row;
  - the Cover Grid home;
  - Controls > Front Buttons (`SettingsList.h`, `SettingsActivity::rebuildSettingsLists()`, `ControlsOptionsActivity`);
  - Quick Actions' Long Back and Long Menu triggers;
  - the Home/Reader shortcut (`QuickActions::isActionAvailable()`, since the second key-access audit);
  - the key help in File Browser, Nearby transfer and Home;
  - Settings > Display > Sunlight Fading Fix (`getSettingsList()`), so Silkscreen keeps the row whether or not its touch panel answered, as in CrossPoint.

  These routed gates use `deviceHasFrontButtons(gpio)`, which equals the old `!gpio.hasTouch()` on every other board. The gates the port added, the light panel's key entry points (`frontlightPanelFromKeys()`: Light Controls in Settings > Display > Frontlight, in the reader menu and as a shortcut) and the panel's Up/Down warmth keys and key steps, use `boardHasFrontButtons()` (the board profile) instead, so an X4 Pro whose touch panel fails its probe gains none of them.

  Key-route fixes that only Silkscreen needs (held Back discarding a Reading Stats date edit, Right creating a clipping in a dictionary lookup, the OPDS search and Wi-Fi network-list input leaks, the frontlight time picker's labels and 5-minute step) use `boardKeepsKeysBesideTouch()` instead: the board profile's keys-beside-touch flag (`TouchConfig::buttonsAlongsideTouch`, read as it is: the touch probe never changes it, so it holds with the touch tail fitted or not, where a test on `BoardConfig::hasTouch()` is false without the tail). Only Silkscreen's profile sets it, so it is false on every keys-only board as well as every touch-only one, and X3/X4, the X4 Pro, Sticky and Paper Mono keep their behaviour exactly. The one other board that answers true is the 3.68" variant, from the build: its profile has no touch panel and cannot set the flag, and these fixes are key routes that need none ([The 3.68" variant](#the-368-variant)).

  **Key hints on touch layouts.** Settings > Display > Key hints on touch screens (`showKeyHintsOnTouch`, on by default; the row and the web setting exist only where a touch panel and the front keys are both fitted) decides whether the touch layouts that otherwise show no key labels draw them. `shouldDrawKeyHints(gpio)` in `include/DeviceCapabilities.h` is the one test: true without a touch panel, false on a touch-only board, the setting on a touch unit with keys. The screens that always drew the band on Silkscreen (Home, Library and its scan screen's Cancel hint, Settings, the Nearby menus, KOReader sync's progress choice, ...) are not affected by it. With the setting on, these touch layouts draw their labels:
  - the hint band under the touch buttons of ClearCache, Nearby stats sync, Nearby position sync, Nearby book transfer (offer, collision and result prompts), the clipping detail, IntervalSelection (Back, Select, `-`, `+`, and a line for the side buttons' large step, below), and the dictionary lookup's alternate-form prompt. Each lays its touch buttons out in `UITheme::getScreenSafeArea(renderer, true, false)`, which already excludes the band in all four orientations, so nothing overlaps it. IntervalSelection used to lay out its touch layout on the full screen, so its safe area now follows the same test (`shouldDrawKeyHints()`) in `render()` and `loop()`;
  - Calibre's connection-failed screen, which waited for Back with no hint on any board, gets one on a touch unit with keys only;
  - the reader menu's sheet: a line above its tab bar (`keyHintLineText()`), which is where the key layout's band would sit. The Root line is about 560 px at the default UI scale and 670 px at Large, over a 474 px portrait panel, so `keyHintLineCount()` measures it and the line wraps onto a second one when it does not fit. `drawerHeight()` grows the sheet by those lines, so the list keeps its rows. The Spacing, Margins and Auto Page Turn panes name their keys in the step hints under their sliders instead (`showsStepHints()` follows the setting; `drawerHeight()` grows the Auto Page Turn sheet, as it does Spacing and Margins, until the slider and both hint lines fit above its Confirm button, which landscape needs: the 65 % sheet leaves about 100 px for a 150 px block). The panes Go to % and Go to Page never open on this layout;
  - the light panel: two lines at the foot of its sheet (`keyHintsShown`; the brightness and warmth line wraps onto a second one at the Large UI scale), added to `panelBottom` only when the taller panel still fits the screen;
  - IntervalSelection's side-step line (`showsSideStepHint()`: touch hardware, `shouldDrawKeyHints()` and a large step that differs from the small one): `drawStepHintLine()`'s "Side buttons: 5 min" for Up and Down, the text the layout without touch draws. The plain touch controls (Auto Page Turn, the idle threshold) carry it 8 px under their step controls, drawn only while it ends above the first action button (36 px to spare in landscape). The slider layout carries it 8 px under the slider: the centred slider (no preview) just needs the body to hold row and line, and the slider seated at the foot of a preview takes the line's 28 px from the preview, only while the preview keeps `MIN_PREVIEW_AREA_WITH_HINT` (120 px). By arithmetic with the Lyra metrics, the preview is about 392 px in portrait and keeps 364, and is 112 px held sideways (122 at the small UI scale), so Settings' margin and line spacing pickers go without the line there;
  - the keyboard: a few tip lines between the text field and the keys, as many as that gap holds, the first line first. Cursor mode names the way back to the keyboard, Left and Right for the cursor and, in a password field, the show/hide switch (or, with the switch selected, the switch and the way back to the cursor); typing with text in the field names the hold-Up edit key and hold-DEL clear. They are the strings the layout without touch draws, in the same cases; a later line wider than the screen in some translation is dropped. Portrait on Lyra has about 220 px (three lines need 68), minus 30 px per wrapped line of text; held sideways the gap is about 4 px and nothing is drawn. The keyboard's own band was already drawn.

  Still left out on purpose:
  - the side-button hints (`BaseTheme`/`LyraTheme::drawSideButtonHints()`, the keyboard's `>` `<`): their only caller is the keyboard, whose touch layout (56-px keys) starts at about y 430-490 in portrait, under the hints' fixed 345-506 band at the right edge, so they would cover its top-right keys; the key layout without touch starts below them;
  - IntervalSelection's front step line, which the band's `-` and `+` label and which would share the room of its touch step controls (its hint band is drawn);
  - the keyboard's "Tips:" header and its lines for the secondary characters, the URL snippets and leaving URL mode (the cursor, password and clear lines are drawn, above), which need more room than the taller touch keyboard leaves.

  On the reader menu's sub-lists the front Left and Right keys, which only switch tabs on the Root pane, step the rows on Silkscreen (`frontKeysStepRows()`, `boardKeepsKeysBesideTouch()`), so the key layout's band can label them Up and Down there, as the edge-button boards do.

  `STR_FRONT_BTN_FOLLOW_ORIENTATION` in `getSettingsList()`'s touch erase names no setting in CrossInk; the front-key orientation setting is `frontButtonOrientationAware` under Controls > Front Buttons, which is routed.
- **Network OTA and the Nearby screens kept**, reworked with battery limits on Silkscreen only ([POWER.md §3.1](POWER.md#31-network-screens-aw-02), CI-06).
  - OTA queries `uxjulia/CrossInk`'s releases, which carry no `firmware-silkscreen` asset, so a check ends at "no update".
  - Pointing it at a private feed is a `-DCROSSINK_OTA_RELEASE_URL=...` build flag (`src/network/OtaUpdater.cpp`).
- **Awake ceiling on battery:** the longer of 15 min and the user's sleep timeout. It never shortens a timeout the user chose; it bounds Never and the keep-awake screens. The 60-min input cap and the low-battery cutoff stay. CrossPoint uses the same rule.
- **Base:** `development` `9dd334d3` as cloned, not `release/v1.6.1`; later merges are in the sync records below.
- **Platform:** the Silkscreen envs override `platform` to pioarduino 55.03.311 (Arduino 3.3.11), the core the Silkscreen sleep path and front light were validated on. `[base]` keeps CrossInk's 55.03.37 for every other env.
- **Board tag** `silkscreen`, the same as CrossPoint, and one SD card shared by both readers (C11 below).
- **Sleep path:** Silkscreen reaches the SDK sleep path, and every other board keeps CrossInk's tail byte for byte. The guard script documents that one exception ([POWER.md](POWER.md#guard-script-and-its-exception)).
- **Automatic page turns count as client traffic.** They extend the ceiling, not the input cap.
- **`.gitmodules`** names `https://github.com/iandchasse/freeink-sdk.git`, branch `silkscreen`, as CrossPoint does, with local overrides ([Repository layout](#repository-layout-and-remotes)).
- **SDK pin:** always the shared head, never CrossInk's pre-merge PR pins.
- **Wake:** CrossInk's short-press-wake setting is kept, defaulting to the long press (Short Power Button = Ignore).
- **Registration:** Silkscreen is registered only in build-relevant files. The release workflows, the release catalog and `docs/catalog` are untouched.
- **Framebuffer:** `FREEINK_FB_PSRAM` is not set, as in CrossPoint, so the framebuffer stays in internal RAM.
- **Front light:** probed only on a user action or a restore at wake. CrossInk's daily light schedule counts as a restore and respects the SDK's no-load and missing-string memory.
- **Battery percentage: tracked in 1% steps, shown in 5% steps** (CrossPoint `844dde61`, with the SDK's `BatteryMonitor::percentTenthsFromMillivolts()` from `bf196c8`; the 5% display step is CrossPoint `75ae9a29`). Upstream snaps the percentage to 10% notches (one noisy ADC read looked up in an 11-entry Li-ion curve). Silkscreen has no fuel gauge, so `HalPowerManager::getBatteryPercentage()` averages 16 conversions of `P+` and reads the same curve linearly between its notches (tenths of a percent), smooths it as before and rounds to the nearest percent, so a cell resting just under 4.20 V still reads 100%. The smoothing step (a tenth of the gap to the new sample) rounds to nearest in both directions on Silkscreen: the other boards' truncating form stops up to 0.9% short of a rising target, which would leave a full cell at 99% until the next boot, and rounding only upward would leave an empty one at 1%. The cache settles within 0.4% of the sample either way. The tracked step is as fine as the hardware resolves; the accuracy is the voltage's (ADC calibration, sag under load, the rise while charging), so it is a state-of-charge estimate, not a gauge. **What the screen shows is that percent cut to 5% steps** (user decision of 2026-10-04: a 1% figure read off a cell voltage is falsely precise, a nine-hour sleep had shown 83 to 82 on rounding noise alone, and the reading rises 10-15% while USB charges, which is the charger path's physics and is not corrected). `silkscreenShownPercent()`, a `constexpr` helper in an anonymous namespace of `lib/hal/HalPowerManager.cpp` with `static_assert` tests (an exhaustive 0-100 loop included), truncates down to a multiple of 5 and returns 100 from 98 up, so a full cell resting off the charger (about 4.18 V, 98-99%) reads 100 and not 95: 4 shows 0, 83 shows 80, 97 shows 95, 99 shows 100. Only the returned number changes: the tenths average, the raw millivolts, the low-battery cutoff, the firmware-update gate and the battery log keep their raw values. The consumers of the shown value (audited 2026-10-05) are the header and status-bar battery labels and icons (`BaseTheme::drawBatteryLeft()`, `drawBatteryRight()` and `drawReaderStatusBar()`, which every theme uses: none overrides `fillBatteryIcon()`), the sleep screen (which measures its label at a fixed 100) and `loop()`'s once-a-minute USB poll, which only asks whether the shown value changed and so now repaints per 5% instead of per 1%. There is no low-battery popup, no web or serial report and no Wi-Fi gate on the percentage in this app. Nothing treats 0 as special, and 1 to 4 can no longer show. The icon's three bars, which light above 10, 40 and 70%, now light at 15, 45 and 75%, since they read the shown value. **The `silkscreen-batlog` image keeps the 1% steps:** the helper, its tests and the return that uses them sit inside `#if FREEINK_DEVICE_SILKSCREEN && !SILKSCREEN_BATLOG` (the helper and its tests above `getBatteryPercentage()`, the return inside it), so what that image's screen shows still matches the log: `e_ui` and `w_ui` are tenths of a percent from the raw cache and the first fresh burst, which the display step never touches, and the analyzer's `ui_pct()` derives the percent the screen showed from them. That image is the size it was (5,625,565 B flash, 116,080 B RAM). The device term of the guard is what leaves every other board's code as it was: `isSilkscreen()` tests the mutable `BoardConfig::ACTIVE`, so the compiler cannot fold it away. The release image grows by 28 B (`silkscreen` 5,616,853 to 5,616,881 B, RAM unchanged at 115,536 B). Gated by `BoardConfig::isSilkscreen()`: every other board keeps the 10% notches and its floor.

## Key access

Every function must be reachable with the keys alone, and touch must keep working beside them. The keys that matter here are Back, Confirm, Left, Right, Up, Down and Power; there is no Home key, and the two side keys share one ADC ladder, so Up and Down never read as pressed together. **C1** is a board with the touch tail fitted, **C2** one without it.

The key-access audit (the `silkscreen-key-access-audit` skill, run on the tree after the `3efe61b6` merge) found 32 gaps: 1 blocker, 6 major, 25 minor. Its ids appear below as B1, M1-M6 and m1-m25. The user chose batches D, A, B, C, E, F, H and G, with a Settings toggle for G. The commits are the "Key access" row of the [Status](#status) table. A second audit, run after the `6fbc97d1` merge and the battery log, is under [Second round](#second-round-where-each-function-is-reached); its commits are the "second audit" rows of the same table.

**Gates.** Each new behaviour is behind a test that is false on every other board, so those boards act as before. The three helpers in `include/DeviceCapabilities.h` are described under [Defaults chosen](#defaults-chosen):
- `deviceHasFrontButtons(gpio)`: true without a touch panel and on Silkscreen with it, false on Sticky and the X4 Pro. It gives a screen that kept a touch layout and dropped its key code the key code back on C1; C2 already had it.
- `boardHasFrontButtons()`: the same from the board profile, for the light-panel entry points (`frontlightPanelFromKeys()`) and the panel's key steps.
- `boardKeepsKeysBesideTouch()`: the profile's keys-beside-touch flag (`TouchConfig::buttonsAlongsideTouch`), true on Silkscreen with the touch tail fitted (C1) and without it (C2). It is not `BoardConfig::hasTouch() && hasFrontButtons()`: Silkscreen's touch panel is optional, and when neither controller answers the probe sets the profile's controller to None, so `hasTouch()` is false on C2 and a test built on it never fires there (the first form of this helper did exactly that, and made the second audit's C2 fixes dead until it was corrected). The flag itself is never changed, and no other profile sets it, so the fixes that only Silkscreen needs leave X3, X4, X4 Classic, the X4 Pro, Sticky and Paper Mono as they were. Under `FREEINK_SILKSCREEN_368` it answers true from the build, as it does on C2 ([The 3.68" variant](#the-368-variant)).
- `swipeSelectsFirstRow()` (`src/components/UiAppHelpers.h`, second round): `hasTouchHardware() && deviceHasFrontButtons(gpio)`, true only on a touch unit that keeps its front keys (C1). A keys-only board has no swipe and a touch-only board no front keys.

The one ungated change is `ButtonNavigator` (below).

**Battery.** None of these adds a wake source, a timer or a task. The front light is lit only by a user action, as before: Light Controls opens the panel dark, and a step from 0 % or Confirm in the panel is the user's switch-on, which still goes through `HalFrontlight`'s probe and restore refusal ([drain checklist](#drain-checklist), item 10). The panel's faster key repeat is a different interval of the same `ButtonNavigator`, and its keys stay idle while the opening key is held.

## Battery log

The battery sleep/wake log is its own build, `silkscreen-batlog`: `silkscreen`'s flags plus `-DSILKSCREEN_BATLOG=1` and the version `1.6.1-silkscreen-batlog`, with nothing else added, so boot timing and the ghost-wake path match `silkscreen`. It appends one CSV row per sleep/wake cycle to `/silkscreen-battery/battery.csv` on the card, to find where the charge goes: the cell's volts at sleep and at wake, how the session ended, early re-sleeps, and the time with the light, the radio and the fast clock on. It has no setting, screen, i18n key or Quick Action: flash `silkscreen` to stop. Everything is inside `#if SILKSCREEN_BATLOG`, so every other env compiles to what it did before. The one blocker that runs the other way round is the release image's 5% battery step (`#if FREEINK_DEVICE_SILKSCREEN && !SILKSCREEN_BATLOG`: the helper and its `static_assert`s above `getBatteryPercentage()`, the return inside it; the device term leaves every other board's code as it was): `silkscreen-batlog` keeps the 1% steps, so what its screen shows still matches the log. `e_ui` and `w_ui` are tenths of a percent from the raw cache and the first fresh burst, which the display step never touches, and the analyzer's `ui_pct()` derives the percent the screen showed from them. That is the one thing besides the log that the image does differently from `silkscreen`.

- [BATTERY-LOG.md](BATTERY-LOG.md) says what differs on CrossInk and where the hooks are. The manual (a campaign, retrieving the file, the columns, the analyzer, the bench proof and the DMM recipe) is CrossPoint's `crosspoint-reader/docs/silkscreen/BATTERY-LOG.md`.
- The SDK half (the RTC record, the ADC burst, the sleep tail) is on the shared SDK line, shared with CrossPoint. The SD writer is CrossPoint's file with one line and one include different: keep the two in step. The analyzer stays in CrossPoint.
- The drain rule is item 11 of the [drain checklist](#drain-checklist) and POWER.md BL-01.
- After each sync, re-check the SDK's BatteryLog files and the hooks; `crosspoint-reader/scripts/silkscreen/upstream_status.sh` reports a missing one.

## The 3.68" variant

`silkscreen-368` is the same board with the Xteink X3's 3.68" panel (792x528: the UC8253, or the UC8279d some X3 batches carry) on J2 in place of the 4.26" one, and no touch tail. It is the owner's "x3 build": the board cut at its cut line, UP(2) as the power key, a 500 mAh cell. It stays the same device, `FREEINK_DEVICE_SILKSCREEN` and `Board::Silkscreen`, so the key ladders, the power policy, the front light, the battery log and the 5% battery step apply as they stand. **Nothing has run on a board.**

- **The switch.** `-DSILKSCREEN_PANEL_368=1` (the SDK's `BoardConfig.h`, default 0), set by `[silkscreen368]` in `platformio.ini`. The SDK derives `FREEINK_SILKSCREEN_368` from it and the device flag, and that is the macro the app tests. With the switch at 0 every other env preprocesses to the text it had.
- **The SDK half** is CrossPoint's stage: 23 commits on the shared line (`c875022` to `48be3d0`, listed in the [sync record](#upstream-merges)). The derived `SILKSCREEN_368` profile (792x528, UC8253 by default, `NO_TOUCH`, the pins and policy of `SILKSCREEN`, asserted equal); the X3 drivers linked and the SSD1677 and UC8279 X4 drivers not; `FREEINK_CAP_TOUCH` 0 and asserted; the X3's own VER probe in place of the generic one; the `BUSY_N` pull-up and cached-controller guard for the X3 drivers' two-phase `BUSY_N`; a driver-free panel sleep that knows the UC8253; the facade in X3 mode from its constructor. CrossPoint's `docs/silkscreen/MODULARITY.md`, section "The 3.68" variant", describes it, and its `TEST-SUITE.md` section "The 3.68" variant" has the bench list ([TEST-SUITE.md](TEST-SUITE.md#the-368-variant-silkscreen-368-test)).
- **The app half** asks the panel where the code means the panel. `HalDisplay::isX3Panel()` is the SDK's `isX3Mode()` in a variant build and the unchanged `gpio.deviceIsX3()` in every other, kept in `#else` so the existing envs compile to the same bytes. `deviceHasX3Panel()` in `include/DeviceCapabilities.h` asks it from `src/`; the simulator's HAL has no such query and no such board, so there it answers `gpio.deviceIsX3()`, as the helpers beside it do. `gpio.deviceIsX3()` stays "the X3 board" (its gauge, USB poll, edge keys and name), and `isXteinkDevice()` and `hasEdgeSideButtons()` stay false for Silkscreen.

- **Envs, tag, version.** `silkscreen-368` is `silkscreen`'s flags and log level on `[silkscreen368]`; `silkscreen-368-batlog` adds `-DSILKSCREEN_BATLOG=1` ([BATTERY-LOG.md](BATTERY-LOG.md)). No `${silkscreen.touch_flags}`, and no touch at all: `-DCROSSINK_APP_CAP_TOUCH=0` and `-DFREEINK_CAP_TOUCH=0` (a mismatch is an `#error`, `include/AppCapabilities.h`). The board tag is `silkscreen-368` for both, so OTA and the SD update refuse a `silkscreen` image and the other way round, and CrossPoint's `silkscreen-368` image is accepted. The firmware device type, which names the asset (`firmware-<type>.bin`, and `firmware-<type>-v<version>.bin` for a release), is **`silkscreen368`**, not `silkscreen-368`: `OtaUpdater.cpp`'s `isMatchingFirmwareAssetName()` takes `firmware-<type>.bin` and `firmware-<type>-<anything>.bin`, so the 4.26" board's type `silkscreen` would have taken `firmware-silkscreen-368.bin` as its own, and `commitAsset()` keeps the first match, so a release that listed the variant's asset first would have left that board with no usable offer (the tag would have refused the image at the flasher, so nothing wrong could boot). A type that does not continue another one past a hyphen cannot collide, and `scripts/test_build_identity.py` checks that for every env. The tag may differ from the type, as `x4pro` and `x4-pro` do. The versions are `<x.y.z>-silkscreen-368` and `<x.y.z>-368-silkscreen-batlog` (`scripts/git_branch.py`): the battery-log analyzer reads a `-silkscreen-batlog` ending as CrossInk's, with its 500 ms early-wake limit.
- **Audits.** The post-link `scripts/check_app_touch_gate.py` (the app's touch symbols, as for the X4 Classic) runs in the build. `scripts/silkscreen/check_no_touch.sh <env>` is CrossPoint's script less its test-firmware checks, and `build_matrix.sh` runs it for every `silkscreen-368*` image: no touch driver body linked (matched by demangled name and by mangled name, so GCC's `$isra$0` and `$constprop$0` clones count), no SSD1677, UC8279 X4 or generic-probe symbol, the X3 drivers linked, and the one board tag. It has no size cap: `InputManager::resetAndHibernateTouch()` is not in this image at all (nothing calls it with `FREEINK_CAP_TOUCH=0`, so `--gc-sections` drops it; it is 255 bytes in the 4.26" board's), and a cap on a symbol that is absent measured nothing. Its patterns are names that depend on `--gc-sections` and inlining, and a pattern that matches nothing passes, so `build_matrix.sh` also runs the script on the 4.26" board's `silkscreen` image after the variant's and requires it to fail on the touch and SSD1677 names: the control. The sleep-wake guard scans the same trees as before. All pass.
- **Drain.** No new wake source, timer, task, hold or pull. The sleep path, `parkedPins`, the ladders, the light and the power policy are the 4.26" board's, and the guard passes in every build. Awake, the X3's stock probe costs about 111 ms at a cold boot (410 ms at most) and nothing at a deep-sleep wake with a conclusive verdict (VER `0x66` or `0xFF`; any other id runs the UC8253 driver and is probed at every wake). `setup()` resolves the controller before the Quick Resume decision, which moves that probe earlier within the same boot and adds none. The `BUSY_N` pull-up is on for the whole awake time and off in sleep; about 73 µA flows through it only while the controller drives `BUSY_N` LOW, in a refresh wait. The X3 drivers have costs of their own, which CrossPoint's POWER.md prices in its section "The 3.68" variant" (computed from the driver code, not measured, and the same SDK here): the UC8253's `begin()` writes both 52,272 B planes white, about 95-110 ms more than the SSD1677's at every `display.begin()` (a cold boot, and each wake that reaches the UI; the UC8279d does not fill); a Quick Resume wake rebases the controller RAM in about 85-110 ms of SPI-bound CPU with no refresh, and in exchange paints the first page as a FAST differential instead of the HALF that `HalDisplay` would turn into a full sync; the worst case for one UC8253 wake is about 190-220 ms; and a HALF anywhere is a full sync with one conditioning pass, the X3 panel's own cost, which `isX3Panel()` switches on for the variant. Saved against the 4.26" board with its tail: the 307 ms touch reset and settle at each cold boot, and the NACKed hibernate write at each sleep entry. The panel's deep-sleep current is not in hand (POWER.md row 17). Two of the SDK's guards for this panel have never run on a board, and their cost is not measured: a `BUSY_N` that stays LOW 300 ms after a deep-sleep wake's reset drops the cached verdict and restarts, which costs a boot and the 111 ms probe, and would cost them at every wake if it repeated (P1 then reads `reset=SW source=probed` after what should have been a wake: step 8 of CrossPoint's bench list); and the reset loop's driver-free panel sleep waits 60 ms between the panel's reset and its sleep command, which only a host test over a recording GPIO model (`run_sleep_panel.py` in the SDK) has exercised (step 10). The key-access gate adds none of this: its routes run in an open screen's `loop()` on a key event, with no timer, task or wake source.
- **Key access.** The variant is a button-only image (`CROSSINK_APP_CAP_TOUCH=0`): it runs the X4's keys-only code, so every function it has is reached by keys, and the light's routes (`frontlightPanelFromKeys()`, `boardHasFrontButtons()`) hold. The routes the two key-access audits added gate on `boardKeepsKeysBesideTouch()`, which reads the profile's `buttonsAlongsideTouch`. A 4.26" Silkscreen without its tail has the flag set; this profile has no touch panel and cannot (the SDK asserts it: `silkscreen_368::noTouch()`), so the first build of the variant had all of them off. The helper now answers true from the build under `FREEINK_SILKSCREEN_368` (`include/DeviceCapabilities.h`, `1ca3131c`), as it does on that board, after the key-access audit of this image (read-only, 2026-10-11) went through all 27 code references: 21 are key routes that need no touch panel and 6 do not change.
  - **What it turns on** (11 features): a held Back or held Confirm opening Quick Actions in TXT and XTC books; the Cover Grid Home's Reading Stats shortcut (the theme is there: the variant has PSRAM); the image viewer's held-Confirm menu and its "Hold Select for Menu" line; Left and Right stepping the rows of a Settings submenu; the reader menu's Dark Mode row and Left and Right stepping its sub-lists, labelled Up and Down; the light panel's two key-hint lines; the schedule picker's field keys, tip and 5-minute step; the Reading Stats date editor's hold-Back discard; Right as Clip in a dictionary lookup (the definition and the not-found and alternate-form prompts); the OPDS search key leaving the selection alone; and the Wi-Fi list's Confirm release not connecting to row 0.

  - **The reader menu is the X4's, not C2's.** `CROSSINK_APP_READER_SAMPLE_PREVIEW` is `!CROSSINK_APP_CAP_TOUCH`, so the variant gets the keys-only X4's full-screen menu with its live sample preview, and `readerDrawerUsesFullScreen()` is true whatever the helper says. ## The shared SDK

There is one Silkscreen SDK line: the branch `silkscreen` of `silkscreen-firmware/crosspoint-reader/freeink-sdk`, published as `iandchasse/freeink-sdk`. CrossPoint owns it. CrossInk's gitlink is **always that branch's head**: never a commit that is not on it, and never CrossInk's own pre-merge PR pins.

```bash

```

**Moving to a new shared head** is always a fast-forward, landed as a `chore:` commit:

```bash
git -C freeink-sdk fetch silkscreen-sdk
git -C freeink-sdk merge-base --is-ancestor HEAD silkscreen-sdk/silkscreen   # must succeed

git add freeink-sdk
git commit -m "chore: move freeink-sdk to the shared SDK head"
```

### Drain checklist

Run after every merge and after any change to sleep, boot, `loop()`, network, USB or front-light code:

1. **Guard:** `python scripts/check_sleep_wake_sources.py` passes.
2. **Keep-awake screens:** `rg "preventAutoSleep\(\) override|skipLoopDelay\(\) override" src`. Each new or changed screen either holds auto-sleep off only while it works, bounded by its own timeout, or is gated on `radioidle::enabled()` like its neighbours ([POWER.md §3.1](POWER.md#31-network-screens-aw-02)).
3. **Radio starts:** `rg "WiFi\.(mode|begin|softAP)|esp_now_init|startRadio|beginEspNow" src`. A screen that brings the radio up must switch it off at its result screens. A new shortcut that starts the radio goes into `radioShortcutRefused()` (CI-05). A new network-boot screen keeps its restart on exit, with a `radioReleased` flag where it releases the radio early.
4. **`loop()` order:** nothing new may return from `loop()` before `sleepOnBatteryAwakeLimits()`, except the exclusive-storage branch (CI-02).
5. **Sleep entries:** `rg "esp_deep_sleep|startDeepSleep|enterDeepSleep\(" src lib`. Every sleep goes through `enterDeepSleep()` or `HalPowerManager`. New SD writes in `enterDeepSleep()` come before `Storage.shutdown()`.
6. **Restarts:** `rg "ESP\.restart|esp_restart" src`. A restart that continues the session goes through `restartWithSilentToken()`, so it carries the awake clocks (CI-04).
7. **Blocking transfers:** a new download, upload, scan or sync that blocks the loop polls `powerManager.lowBatteryCutoffTripped()` in its abort or cancel path (BAT-01). `HttpDownloader` users get it for free; the web upload cancel hook and the Library scan's cancel poll carry it since `a681d04a`; WebDAV GET and PUT and `/download` (through `CutoffAbortPrint`) and the stats and clippings uploads (`StatsUploadClient`) since `aa3f8544`. A client or stream that does not go through `HttpDownloader` needs its own poll: the uploads were the miss the `67100e66` sync found.
8. **Client traffic:** a new web endpoint that clients poll on their own does not count as traffic (the middleware in `CrossPointWebServer::begin()`).
9. **Input:** a new input path counts as input only when the user meant it. Quick Lock rejections do not (CI-03).
10. **Front light:** a new path that switches the light on goes through `HalFrontlight`, so the probe and the restore refusal apply. Nothing lights it before the wake decision.
11. **Wake sources, timers, tasks:** nothing new runs in sleep or arms a wake (ZD-01). Nothing new runs before the wake decision in `setup()` (WK-01). The battery log's hooks keep this: the release-wake and reset-loop exits call none, the early-ghost exit stores RTC words only, and the one ADC burst before sleep is taken under a 20 ms bound (POWER.md BL-01).
12. **Simulator:** every new HAL call from `src/` is under `#ifndef SIMULATOR` or behind a shim.
13. **Front-key UI:** a new `hasTouch()` gate that is really about the front keys uses `deviceHasFrontButtons()` or `boardHasFrontButtons()` instead. New HAL methods avoid the names `scripts/check_app_touch_gate.py` forbids. A key route that only Silkscreen needs uses `boardKeepsKeysBesideTouch()`, which is true on the 3.68" variant too (from the build), so it needs no case of its own there.
14. **Rules:** re-read every row of [POWER.md §3](POWER.md#3-firmware-rules-and-where-they-live) whose code the merge touched.
15. **3.68" variant:** every `gpio.deviceIsX3()` or `Board::XteinkX3*` test the merge brought is read as panel or board. A refresh mode, a gray base, a layout or a sleep-screen choice asks `deviceHasX3Panel()` (`HalDisplay::isX3Panel()`); the gauge, the USB poll, the edge keys and the names stay on the board test. `silkscreen-368` and `silkscreen-368-batlog` build, `scripts/silkscreen/check_no_touch.sh` passes for each, and nothing the merge brought gives the variant a wake source, timer, hold or pull: its sleep path, parked pins, ladders and light are the 4.26" board's. `upstream_status.sh`'s CrossInk lens asks four `isX3Panel()` lines of `lib/hal/HalDisplay.cpp` and one `display.isX3Panel()` in `main.cpp`. `HalDisplay.cpp` has five (`displayBuffer()`, `displayBufferAsync()`, both `displayGrayscaleBase()` and `refreshDisplay()`), so a merge that resolves one back to `gpio.deviceIsX3()` still reads "current": the floor is CrossPoint's (`45ff81d1`), and the fix there is `v368_variant_app "$CI" 5`. The `deviceHasX3Panel()` sites (`main.cpp` twice, `ScreenTransitionRefresh.h`, `SleepActivity.cpp`, the Dashboard and Minimal themes, `SettingsList.cpp`, the web server) it does not count, so read them with this item.

## Simulator and host tests

This host has no C++ compiler, so neither the simulator nor the `test/` CMake suite has run since the port began. Every change was written to compile there, through the gates above. One `test/` target compiles a changed file: `firmware_board_tag` builds `src/network/FirmwareBoardTag.cpp` for Sticky, so the new Silkscreen branch is never reached. The same holds for the `silkscreen-368` branch added to it, so it was checked another way: the production `FirmwareBoardTag.cpp` was compiled with MSVC BuildTools 2022 (installed on this host: the SDK stage of the variant found it, and the sentence above predates that) for six flag sets against a stub `BoardConfig.h` (the two Silkscreen tags, X4 Pro, X4 Classic, X3 and X4, Sticky). Each prints its own name, accepts its own tag and rejects the others', `silkscreen` against `silkscreen-368` included. `scripts/test_build_identity.py` ran with the new envs (it checks their versions, and that the log image's keeps its `-silkscreen-batlog` ending). The new `deviceHasX3Panel()` is behind `#ifdef SIMULATOR` like the helpers beside it, so the simulator builds are unchanged; they were not run. `option_popup` gets `BaseTheme.h` and `UITheme.h` from its own stubs (`test/option_popup/stubs`), not the changed `src` headers.

The key-access fixes added cases that have not run either: `test/reader_drawer_model/ReaderDrawerModelTest.cpp` gained the Light Controls row and the two light-panel predicates (`ReaderDrawerAvailability::lightControls` is its last field, so the positional initialisers there keep their meaning, and the new full-catalog case lists all ten flags), and `src/simulator/SimulatorSmokeTest.cpp` checks the Light Controls shortcut values (offered only where `frontlightPanelFromKeys()` holds, never as a chord, kept by a Quick Actions slot).

The second audit's fixes added cases that have not run either: `ReaderDrawerModelTest` gained the `readerDrawerUsesFullScreen` truth table, the `readerDrawerShowsBookBand` cases and the Dark Mode row (last in the More tab, the action enum appended, every tab within the catalog's 13 slots), and `SimulatorSmokeTest` checks that the Home/Reader shortcut is offered exactly where `deviceHasFrontButtons()` holds, that a Home/Reader Quick Actions slot is kept only where `boardKeepsKeysBesideTouch()` holds (the simulator's helper never is, so it expects the reset there) and that the Disable Touchscreen row follows its gate. The gated paths are false in every simulator profile, so the simulator checks only that the other boards are unchanged.

On Linux or macOS (or WSL; see `docs/simulator.md` for the macOS-only paths), run:

```bash
pio run -e simulator
pio run -e x4-pro-simulator
pio run -e sticky-simulator
python scripts/run_simulator_smoke_test.py
```

Also run the `test/` CTest suite.

**`x4-pro-simulator` is the closest to Silkscreen.** CrossInk has no Silkscreen simulator profile; the X4 Pro profile approximates touch and keys together:

- touch input and the keys (arrows, Return, Escape, P, and H for the X4 Pro's Home key) both work;
- the front light is a PWM light.

It differs from Silkscreen in three ways:

- **Front-key UI.** The front-key helpers fall back to `!hasTouch()` in the simulator, so it shows the X4 Pro's touch-board UI: no hint band, no Front Buttons settings. Check that side in `simulator`, the keys-only profile, which draws them.
- **No Silkscreen code.** Every Silkscreen mechanism (`FREEINK_CAP_POWER_POLICY`, the front-light probe, the radio rules) is compiled out of every simulator env.
- **What it is for.** The simulator checks that the shared code builds and that the other boards' UI is unchanged. Silkscreen's own behaviour needs the board (C1-C12).
